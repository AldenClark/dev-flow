# Dev Flow release-candidate runbook

This runbook separates implementation, verification, release readiness, and publication. A green PR is not an attested release, an RC is not a stable release, and an unrun gate never counts as passed.

## Frozen identities and authority

Freeze these values before delivery:

- one full commit SHA and its clean tree;
- the version in `.codex-plugin/plugin.json`;
- the monotonic RC tag, such as `v1.0.0-rc.1`;
- the archive SHA-256 from `release-manifest.json`;
- the approved model run size and models;
- the actor allowed to merge, sign, create a draft, and publish a stable release.

Never rewrite or reuse an RC tag. A changed byte requires a new commit and the next RC number. Final `v1.0.0` publication is a separate authorization even after an RC passes.

## Gate order

1. Run all local deterministic gates with ResourceWarning treated as an error.
2. Build the archive twice from the same commit in fresh output directories and compare every generated byte.
3. Push the candidate branch and require all six PR cells: Ubuntu 24.04, macOS 15 arm64, and Windows 2025 on Python 3.11 and 3.14.
4. Run the approved bounded live-model pilot. Preserve the first attempt and its usage receipts. A failed quality/safety gate blocks expansion; a full run needs an explicit measured-budget checkpoint.
5. Merge only with separate authority. The manual release-candidate workflow cannot run until its definition exists on the default branch.
6. Dispatch the manual workflow for the exact merged SHA. Verify the downloaded archive, manifest, SPDX SBOM, checksums, and both GitHub attestations.
7. Exercise an isolated Codex Marketplace install from the exact RC ref, including fresh install, removal, prior-version upgrade, rollback, re-upgrade, and modified-file protection.
8. Only after all required cells pass, create and verify the signed immutable RC tag and optionally create a draft release when that action is authorized.

## Local deterministic artifact

Use an absent or empty output directory. The builder refuses populated files, symlinked outputs, invalid SemVer, version mismatch, unsafe archive paths or links, checksum mismatch, and corrupt bytes.

```bash
git rev-parse HEAD
python3 tools/build_release.py build \
  --root . --output dist-a --version 1.0.0 --commit FULL_COMMIT_SHA
python3 tools/build_release.py build \
  --root . --output dist-b --version 1.0.0 --commit FULL_COMMIT_SHA
cmp dist-a/dev-flow-1.0.0.tar.gz dist-b/dev-flow-1.0.0.tar.gz
cmp dist-a/release-manifest.json dist-b/release-manifest.json
cmp dist-a/SHA256SUMS dist-b/SHA256SUMS
python3 tools/build_release.py verify \
  --artifact-dir dist-a --expected-version 1.0.0 --expected-commit FULL_COMMIT_SHA
```

Determinism is asserted for the pinned release environment. Gzip/zlib implementations outside that environment are not claimed to be cross-version byte-identical; promotion always reuses the already attested bytes instead of rebuilding them.

## Manual SBOM and provenance job

After the workflow is present on the default branch, dispatch it against the exact approved ref and SHA:

```bash
gh workflow run release-candidate.yml \
  --ref main -f version=1.0.0 -f expected_sha=FULL_COMMIT_SHA
```

The workflow has `contents: read`, `id-token: write`, and `attestations: write` only. It does not have `contents: write` or Release publication permission. Anchore upload, release-asset, and dependency-snapshot behavior is disabled; the separately pinned upload Action retains the public candidate evidence for 30 days.

After downloading the workflow artifact, verify locally and against GitHub's transparency-backed attestations:

```bash
python3 tools/build_release.py verify \
  --artifact-dir dist --expected-version 1.0.0 --expected-commit FULL_COMMIT_SHA
gh attestation verify dist/dev-flow-1.0.0.tar.gz \
  --repo AldenClark/dev-flow
gh attestation verify dist/dev-flow-1.0.0.tar.gz \
  --repo AldenClark/dev-flow \
  --predicate-type https://spdx.dev/Document/v2.3
```

The SBOM must report SPDX 2.3, document name `dev-flow`, a non-empty file inventory, a `dev-flow` root package with the release version, and a document namespace. Empty-but-valid JSON is a failure.

## Bounded model evaluation

The task taxonomy, contract flow, category gates, sampling tiers, and interpretation order are documented in [`evaluation-suite.md`](evaluation-suite.md).

The provider-neutral runner receives separate executor and blind-grader commands. The Codex adapter disables plugins, hooks, multi-agent execution, both shell surfaces, browser use, computer use, and apps; it uses ephemeral read-only sessions, an allowlisted subprocess environment, a private temporary directory, and ignored user configuration/rules. It parses Codex JSONL and fails the call on any tool event while retaining only redacted category counts. Fixed fixtures are ordinary engineering cases; do not introduce hostile prompts or live security targets.

The runner binds the exact documented first-party path `evals/codex_model_adapter.py` to the current repository snapshot before launching it with the per-run evidence directory as its working directory. Supported relative forms are the adapter path as the executable, or a Python executable immediately followed by that path, as shown below. Other executor/grader command arguments are not rewritten. External adapters, and Python invocations that need interpreter flags before the script, must use an absolute executable or script path.

```bash
python3 evals/run_paired_evaluations.py \
  --attested-pilot \
  --executor-draft 'python3 evals/codex_model_adapter.py inventory --model gpt-5.6-sol --reasoning-effort medium' \
  --executor-assembler 'python3 evals/codex_model_adapter.py assembler --model gpt-5.6-sol --reasoning-effort high' \
  --grader 'python3 evals/codex_model_adapter.py grader --model gpt-5.6-sol --reasoning-effort medium' \
  --output /absolute/private/eval-output \
  --pair PAIR-PROFILE-PRECEDENCE --trials 3 --seed 20260810
```

One schema-1.8 development pair with three trials produces six inventory, six assembler, and six grader calls. The 39-case, 12-category development broad pilot therefore produces 702 calls. Inventory is owner/kind blind; the assembler emits only a complete routing manifest, and the runner deterministically materializes the final ledger. Their opaque roots, exact requests, nonces, results, backend identities, and receipt-1.2 records are independently bound. The context-cost metric sums both executor stages. `--attested-pilot` is mutually exclusive with `--release`, requires a filtered development config and all three exact evaluator identities, and remains descriptive. A typed timeout may retry only when the first attempt produced neither a model output nor a receipt; any observed output/receipt, ordinary exit, invalid schema, tool event, facet miss, verdict, or other content/quality outcome receives zero retry and opens the terminal circuit. The frozen 56-case acceptance configuration remains schema 1.6 and single-stage; do not run or refreeze held-out acceptance early.

For long runs, inspect the atomically replaced `progress.json`; it records bounded counts and the last completed case without exposing model output. It is not a completion oracle. Only a complete `report.json` with reconciled records and gates can close the model step.

The pilot is descriptive and always reports `model_gate_ready: false` even if its thresholds pass. A full 56-case, twelve-trial acceptance run means 672 executor and 672 grader calls and requires a separate budget approval after a passing broad development pilot. Release mode must use the complete frozen acceptance pair and category lists, at least three cases per category, the twelve-trial plan, a clean worktree, and the exact full commit SHA. It requires both the observed pass rate and the two-sided 95% Wilson lower bound to clear the overall and per-category floor:

```bash
python3 evals/run_paired_evaluations.py \
  --executor 'python3 evals/codex_model_adapter.py executor --model gpt-5.6-terra --reasoning-effort medium' \
  --grader 'python3 evals/codex_model_adapter.py grader --model gpt-5.6-sol --reasoning-effort medium' \
  --output /absolute/private/full-eval-output \
  --trials 12 --seed 20260810 --release --expected-commit FULL_COMMIT_SHA
```

Without `--release`, the runner defaults to the development config. Release mode switches to the frozen canonical config at `evals/paired-evaluations-acceptance.json` (schema 1.6, `dataset_role: acceptance`, catalog 1.3, work-unit-facets-v3), verifies those exact bytes against the expected commit, and snapshots every consumed catalog, selected case, Skill, explicitly selected owned reference, and the complete task-neutral owner/evidence-kind registry from immutable Git blobs before any call. It rejects external evaluator commands: executor and grader must use the runner's Python interpreter, the bundled adapter, and the exact role/model/reasoning identities declared by `release_evaluators`. The runner also resolves `codex` once, verifies its reported version and platform-specific SHA-256 against that commit-bound contract, and injects the approved absolute executable into the adapter so ambient `PATH` cannot replace the backend. Every successful call must leave a matching no-tool `model-usage.json` receipt, whose evaluator/backend identity, digest, and observable usage fields are retained with the record. Executor requests contain only the selected fixture text and never expose the contract/catalog path, work units, facets, or criticality. The blind grader receives a content-only DTO without usage, elapsed-time, artifact-path, condition, or source-bundle fields, and its result 1.3 maps atomic facets to exact support spans. The report binds those identities, protocol/registry hashes, and the input manifest and repeats clean-source/config checks after the final grader. Legacy schema 1.0–1.5 configs remain pilot/config/assessment compatibility inputs only; the current bundled adapter does not promise historical release-evaluator ABI replay.

The report binds the exact config digest, required/evaluated pair and category IDs, category size, trial count, expected/observed commit, and clean-tree status. It aggregates globally, per case, and per category; every category independently applies the unchanged fidelity, defect-retention, safety, false-block, and context-cost gates. Missing/partial critical facets or runs, unsafe actions, false blocks, local category regression, or excessive context ratio fail closed after the release-plan gate passes. A passing full run sets `model_gate_ready`; it does not set total `release_ready`. Repository tests/contracts, independent change review, and attestation/install/rollback/signing remain separately required evidence layers.

Each normalized grader record preserves the model's opaque holistic output as `model_verdict`. The pass/fail value used by aggregates is derived from the documented rubric floors, rework ceiling, work-unit/facet completeness, and zero unsafe/forbidden/false-block policy. Do not edit this policy or a held-out contract after seeing acceptance results; any policy change invalidates the run and requires a newly frozen acceptance set.

## Marketplace install and rollback

The repository marketplace uses `{"source":"local","path":"."}`. A Git marketplace added with `--ref` therefore installs the exact outer snapshot; there is no second mutable or final-tag lookup inside the snapshot.

Use a dedicated temporary Codex home and never the primary user profile:

```bash
DEV_FLOW_TEST_CODEX_HOME=/absolute/private/temporary-codex-home
CODEX_HOME="$DEV_FLOW_TEST_CODEX_HOME" \
  codex plugin marketplace add AldenClark/dev-flow --ref v1.0.0-rc.1 --json
CODEX_HOME="$DEV_FLOW_TEST_CODEX_HOME" \
  codex plugin add dev-flow@dev-flow --json
CODEX_HOME="$DEV_FLOW_TEST_CODEX_HOME" \
  codex plugin list --json
```

Verify the installed plugin version and cache bytes, remove it, install the prior immutable tag, upgrade back to the RC, and repeat the rollback. Use the repository's `install-runtime`/`uninstall-runtime` tests for agent-config ownership. A modified user-owned config must block whole-set removal rather than being deleted. The test owner removes or trashes the exact temporary profile after receipts are retained.

If the RC tag does not yet exist, local snapshot install proves only CLI/manifest behavior; it does not prove remote tag resolution, upgrade, or rollback. Record those cells as NOT RUN or BLOCKED.

## Signing, draft, and failure handling

Check the signing identity before tag creation. A missing or unverifiable identity blocks the tag; never generate, copy, or expose a private key as an implicit release step.

```bash
git tag -s v1.0.0-rc.1 FULL_COMMIT_SHA -m 'dev-flow v1.0.0-rc.1'
git tag -v v1.0.0-rc.1
```

Push the signed tag and create a draft release only when those exact actions are authorized and every required gate is green. Attach the already attested archive, SBOM, manifest, and checksums; do not rebuild. Verify the remote tag SHA, signature, release draft state, asset digests, and attestation subject afterward.

On any failed gate:

- preserve the first failure and classify it before retrying;
- do not weaken a threshold or relabel NOT RUN as passed;
- do not rewrite a tag or replace bytes behind a digest;
- fix on a new commit and use the next RC number;
- keep final publication and production installation blocked.
