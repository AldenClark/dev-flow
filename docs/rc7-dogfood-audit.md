# Dev Flow RC.7 本地任务回看

> 状态：RC.7 设计输入，不是对单个任务或代理的绩效评价。
> 隐私边界：只保留聚合任务形态、实际调用、纠正类型和证据结果；不记录任务正文、任务 ID、个人信息或本地绝对路径。

## 1. 回看的范围和限制

本次回看扫描了当前主机可见的本地 Codex 任务，并重点检查 RC.5 发布之后仍有活动的根任务。库存中共有 40 个根任务和 228 个子代理会话；其中 10 个根任务在 RC.5 之后有活动，覆盖删除安全审计、发布维护、Git 集成、主机清理、新项目设计、外部系统观察、跨平台实现、测试体系建设和 RC.7 自身设计。

这些任务只用于发现 Dev Flow 的实际优势、摩擦、优先级和代表性回归案例。它们不定义 RC.7 的产品架构，也不把主 Skill 与专业 Skill 的演进路线改造成按历史任务类型编排的流程。

证据来自本地任务元数据、实际工具调用、最终结果、仓库证据和仍在进行任务的当前状态。它能说明 Dev Flow 在这些任务里怎样表现，不能证明某条方法与生产率或正确性之间的因果关系；仍在进行的任务也不能被当作已完成样本。

## 2. 已经有效的部分

### 权限和事实边界已经成为稳定行为

多个不同形态的任务都正确地区分了只读调查、实现、提交、发布和外部动作，没有把前一项自动扩大成后一项。用户修改、嵌套 Git 根、当前分支和工作树状态也被当作受保护输入。这些不是 RC.7 要弱化的“流程”，而是应该保留的少数硬边界。

### 证据环境区分明显提高了结论质量

任务能够区分源码、编译、宿主测试、模拟器、设备、安装、外部系统观察和生产证据；在设备不可用或实时事件没有出现时，结论保持为阻塞或未观察，而不是推断通过。外部系统观察还正确地区分了监控器/解析器自测与真实流量。

### 聚焦的负向控制很有价值

删除安全、测试发现、解析器和发布验证中的负向控制能快速证明 oracle 是否敏感。最好的短任务没有启动完整 Dev Flow 路线，只是读取必要事实、做一个能推翻错误判断的检查，然后给出有边界的结论。

### 专业方法确实改变过决定和证据

在 5 个适合使用方法的匿名观察中，5 个触发了方法，4 个进入可执行结果；已观察到的方法作用包括改变技术决定、改变测试 oracle 和限制完成声明。这个结果支持“方法应在具体困难处被实际使用”，但不支持追求方法调用率或固定轮次。

## 3. 需要 RC.7 解决的问题

### 3.1 路由和 Skill 读取会重复出现

10 个重点根任务在 RC.5 后可识别到 48 次 `route-task`、11 次 `route-agent`、35 次主 Skill 读取和 84 次专业 Skill 读取；8 个任务运行过 `route-task`。其中一部分来自 Dev Flow 自身维护和验证，不能直接视为浪费，但新项目设计与长周期实现中也出现了围绕同一语义目标的重复路由。

RC.7 因此需要把“静默直达”当作产品要求：一个语义目标确定 owner 后继续工作，只有意图、权限、平台、范围或证据计划发生材料变化时才重新路由。续接、工具中断或新增一句细化说明本身不是材料变化。

本轮独立审查派发还暴露了一个更小的 CLI 问题：`route-agent --help` 将 `--risk` 显示为自由参数，却不列出 canonical token，直觉值 `high` 会得到 invalid。RC.7 应让 help 直接列出合法值或接受稳定别名，并保留未知值的明确纠错；维护者不应先读内部 risk contract 才能正确调用公共命令。

### 3.2 文档和审查可能取代产品推进

一个新项目设计样本形成约 3500 行设计资料，并使用四轮、12 个独立审查角色把所有等级 finding 清零。审查发现了崩溃窗口、时间映射、FFI worker、迁移和状态建模等真实问题；但后期继续消除低优先级意见时，文档和审查已经成为主要产出，仍没有产品代码或运行证据。

RC.7 不能以文档长度、审查轮数或 finding 归零作为质量终点。文档必须能使下一项实现、验证、运行或未来维护更可靠；审查在没有未解决的后果性问题、剩余内容只是命名或偏好时停止。

### 3.3 长任务缺少切片级收口

跨平台测试体系和设备实现任务展示了强测试设计、真实环境诚实性和专业诊断能力，但也出现了很长的上下文、大量子代理、磁盘与模拟器资源压力，以及“局部已经通过、整体仍在扩张”的状态。工作树文件数、宿主测试通过或审查数量都不能替代当前切片的用户结果。

RC.7 需要让每个切片先声明一个主要结果和终止条件。切片结束时只做三种决定：结果已证明并停止；出现材料新风险并开启明确的新切片；外部条件不足并诚实阻塞。不能让测试体系、文档体系或审查体系无限成为项目本身。

### 3.4 子代理的独立性有价值，但数量不是质量

重点任务中有 3 个根任务使用子代理，共观察到 43 次根级派发。独立研究、封闭实现和干净上下文审查带来了价值；高度依赖主线语义的任务被切散，或为了继续清低价值 finding 重复派发时，整合成本迅速增加。

RC.7 应要求每个子代理在派发前拥有独立有用的工作产品、清楚 oracle 和 root 集成责任。并发数量由真正独立的工作面决定；已无后果性未知时，不为“多一轮更放心”继续增加代理。

### 3.5 失败分类需要进入共同语言

优秀任务会区分产品缺陷、错误命令、测试 harness、环境/权限不可用和目标平台真实失败。若不分类，错误 scheme、未授权设备或测试发现失败很容易被写成代码失败，随后引发错误修复和额外流程。

RC.7 应在调试、验证和测试系统 Skill 中共享这一最小分类，并要求先保存首个失败，再选择能区分原因的下一项检查。

### 3.6 激活和完成仍然不是效果证明

匿名观察中，Dev Flow 预期适用 8 次、负向对照 2 次；范围符合 10/10，但只有 2 个样本在观察窗口内闭合，6 个证据通过、2 个阻塞、2 个未运行。这说明“正确激活”和“没有越权”是必要条件，不等于任务已经完成，也不证明方法带来净收益。

RC.7 的行为评估必须同时看成果、返工、过程成本和结束质量；持续中的任务保持 `PARTIAL`，不能为获得漂亮指标而推断终态。

## 4. 对 RC.7 设计的直接约束

1. **静默快速路径**：安全、明确、局部的任务不要求读取主 Skill、运行路由或生成文档；主 Skill 未激活时，授权、用户修改和证据边界由明确的宿主/仓库合同承载，Dev Flow 只验证自己没有削弱它们。
2. **语义目标内摊销路由**：一次 owner 选择服务同一个语义目标；只有材料转换才重新判断。
3. **下一动作价值**：每份新文档、每个方法和每次派发都要能说明它将改变哪个下一动作、决定或证据。
4. **方法饱和停止**：一个方法已经消除当前未知时回到开发；不连续堆叠同类框架。
5. **后果性审查停止**：没有未解决的行为、数据、安全、兼容、资源或恢复问题时结束审查，不追求 finding 清零。
6. **切片终止条件**：复杂工作以可观察结果和证据闭合，不以计划完成度、文件数量或测试数量闭合。
7. **有界子代理**：只派发独立有用工作面；root 必须检查源码、diff 和测试并综合结论。
8. **资源与平台边界**：测试体系显式处理设备、模拟器、磁盘、进程和 fixture 所有权，并先运行最窄有效通道。
9. **失败归因**：代码、命令、harness、环境、权限和平台结果分别报告。
10. **保留强边界**：授权、用户修改、精确身份、证据环境和未运行项继续强制执行。

## 5. RC.7 必须能观察到的改善

- 小任务可以不显示 Dev Flow 过程而正确结束。
- 同一语义目标不会因为续接或普通细化反复路由。
- 新增和明显行为变化会在编码前消除材料产品歧义，但不会自动生成整套文档。
- 技术设计至少包含一个可推翻关键选择的证据或简化检查。
- 审查发现真实后果性问题后会修正；只剩偏好项时会停止。
- 长任务每个切片都有明确完成、阻塞或重开理由。
- 子代理带来的独立发现可追踪到最终决定，无法带来独立结果的派发减少。
- 测试结论能说明 oracle 为什么敏感，并准确标记实际运行环境。
- 项目知识被后续任务找到并改变行动；没有这种用途的文档不会成为默认产物。
- RC.6 的授权、脏工作树和证据边界不发生回归。

这些条件由 [RC.7 代表性行为评估参考](./workstreams/dev-flow-2.0-rc.7/acceptance.md) 表达为带负向控制的具名示例。各实施组只选择受影响的示例并将它们纳入现有评估 owner；它们评价开发结果，不要求真实任务输出对应字段或报告，也不形成独立发布门禁。
