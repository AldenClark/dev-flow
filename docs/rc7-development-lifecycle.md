# Dev Flow RC.7 开发指导草案

> 状态：已接受的实施前设计基线；RC.7 source-candidate 已将其核心行为落实到主 Skill、专业 Skills、路由和验证中。
> 目的：帮助 AI 在真实项目里持续做出更好的开发判断，而不是把软件开发改造成一套必须填完的流程表。
> Skill 改造方案：[`rc7-skill-evolution-design.md`](./rc7-skill-evolution-design.md)。
> 真实任务依据：[`rc7-dogfood-audit.md`](./rc7-dogfood-audit.md)。

## 1. 这次真正要解决的问题

Dev Flow 1.x 试图用 packet、状态、记录和门禁把正确过程固定下来。它获得了可追踪性，却把注意力从“当前代码和产品真正需要什么”转移到了“流程是否完整”。上一版 RC.7 草案又走回了同一条路：虽然换成生命周期、交付物和质量合同，仍然是在预先规定所有任务应该经过什么。

RC.7 应当反过来：

- 给 AI 一套稳定的工程取向；
- 教它在关键时刻怎样观察、判断、推进和验证；
- 让复杂度、风险和未知自然增加思考深度；
- 让简单任务保持简单；
- 让有长期价值的理解自然留在项目里；
- 用真实结果和代表性任务检验指导是否有效。

开发流程仍然存在，但它是一条指导工作的主线，不是一台工作流状态机。

## 2. 从主流开发工作流 Skill 学到什么

### 值得吸收

- **从意图和当前证据出发。** BMAD 的 Build 可以接受一句话、issue 或完整 story，先读仓库和已有规划，再选择最小安全路径；其规划工具被明确描述为“独立工具，不是阶段”。
- **让工作量随未知和后果增长。** BMAD 允许明确小改动直接构建；Kiro 同时提供 Quick Spec 和带评审的标准 Spec；Spec Kit 提供去掉模板仪式的 Lean workflow。
- **Skill 应提供判断力，而不是复制百科。** Agent Skills 和 Anthropic 的写作指南都强调简洁、按需加载，并按照任务的脆弱性决定自由度：上下文相关的代码审查给高自由度，危险迁移才给精确步骤。
- **把强指导放在具体失败点。** Superpowers 的调试、TDD、完成前验证等 Skill 围绕一个明确问题给出动作、反模式和停止条件，局部上很有力量。
- **通过真实使用改进 Skill。** Anthropic 和 Superpowers 都强调先观察无 Skill 时模型怎样失败，再用代表性任务验证指导是否真的改变行为。
- **逐步披露上下文。** GSD、Agent Skills 和成熟 Skill 包都会把入口保持较薄，只在当前任务命中时读取详细流程、模板或工具。

### 不应照搬

- Superpowers 的“任何创意工作都必须先 brainstorming，再 writing-plans”的全局链条，对个人偏好明确、仓库事实充分的任务会产生不必要停顿。
- Spec Kit、Kiro 和 GSD 的完整模式都可能产生大量 spec、plan、task、state 和 checkpoint；这些适合某些团队或长周期项目，不应成为 Dev Flow 普通工作的默认成本。
- BMAD 的完整项目路径仍偏重文档和角色。我们要吸收它的按意图缩放与独立工具思想，不复制整套项目管理体系。
- “每个阶段都必须有产物”会再次把产物存在误当成质量。

这些项目给出的共同答案不是某一条标准流程，而是：**薄入口、明确默认、按需加深、具体反馈、保留逃生口。**

## 3. RC.7 的形态：一条薄主线，三层帮助

### 3.1 一条薄主线

任何开发任务都沿着下面的自然循环推进：

```text
看清现实 -> 对准结果 -> 选择下一步 -> 做出一个完整变化 -> 证明它 -> 留下有用知识
                     ^                                      |
                     |________ 新发现随时带回前面 __________|
```

这六个动作不是阶段，也不要求单独记录：

1. **看清现实**：先读真正相关的源码、测试、文档、配置、历史和运行现象。
2. **对准结果**：知道用户或系统最终应观察到什么，以及什么不能被破坏。
3. **选择下一步**：在当前信息下做最有判别力、最小而完整的一步。
4. **做出变化**：让代码、测试和受影响知识一起向目标前进。
5. **证明它**：使用能推翻错误实现的证据，而不是寻找绿色信号。
6. **留下知识**：只把未来仍需要的产品语义、设计理由、操作经验或测试策略放回仓库。

一个拼写修改可以在几分钟内走完这条主线。一个新产品可以在数月中反复循环。两者不需要不同的流程引擎。

### 3.2 三层帮助

#### 第一层：Dev Flow 激活时始终存在的工程取向

- 证据先于猜测；先找现有行为和约定。
- 用户可观察结果先于内部结构。
- 选择满足当前已知需求的最小充分方案。
- 保护既有消费者、用户修改和已证实行为。
- 用新信息修正方向，不维护已经失效的计划。
- 完成声明只覆盖实际检查过的代码和环境。

授权、用户修改保护和证据诚实首先由宿主与仓库指令拥有；Dev Flow 激活时强化这些边界，不能声称在自身未加载时提供它们。所谓“静默快速路径”是不显示路由、文档和方法仪式，不是移除宿主安全边界。RC.7 必须分别验证主 Skill 激活和未激活时的承载者，不能依赖偶然的模型习惯。

#### 第二层：按当前问题调用的开发实践

需求澄清、UX 探索、架构决策、调试、测试设计、代码审查、交付准备等不是固定站点。当前工作出现相应问题时才调用，并在问题解决后回到主线。

#### 第三层：专业方法和工具

状态模型、消融、property testing、威胁模型、MC/DC、TLA+、迁移回放等只在具体结构或风险出现时加载。方法库为判断提供工具，不管理任务生命周期。

## 4. 怎样决定需要多少过程

不要先给任务贴流程等级。观察四件事：

- **未知**：我们是否真正知道要实现什么和现有系统怎样工作？
- **后果**：错误会造成多大影响，是否涉及数据、安全、隐私、钱、兼容或不可逆操作？
- **波及**：有多少消费者、模块、平台、团队和运行环境会受到影响？
- **可逆性**：能否快速发现错误并低成本恢复？

它们决定当前需要多少研究、设计、记录和验证：

| 工作形态 | 通常怎么做 |
|---|---|
| 明确、局部、容易验证 | 读附近事实，直接修改，运行聚焦检查，审阅 diff |
| 已知缺陷 | 复现，找到最早根因，建立回归证据，最小修复 |
| 新增或明显行为变化 | 先把产品结果和关键例外说清，再设计一个最小端到端切片 |
| 行为保持型重构 | 先保护现有行为和消费者，逐步改变结构，比较前后结果 |
| 新项目或陌生领域 | 先做 walking skeleton，通过真实切片逐步发现架构和知识需要 |
| 跨边界或高后果变化 | 增加备选比较、失败/恢复、专业方法、独立视角和更接近目标环境的证据 |
| 发布、部署、迁移 | 在已有工程证据上补精确身份、目标、观察、停止和恢复；另行取得动作授权 |

如果第一步就能消除未知，不需要提前写一套完整方案。如果一个“小改动”持续暴露新边界，它自然升级为更深的工作。

## 5. 在开发的不同位置怎样下手

下面不是必经阶段，而是 AI 在生命周期中经常遇到的工作位置。可以从任意位置进入，也可以按新发现来回移动。

### 5.1 刚接到任务：先找到真正的问题

先做这些：

- 找到实际 Git 根、适用指令、工作树和用户正在修改的内容；
- 追踪最相关的调用路径、测试、合同和运行入口；
- 用一句话复述希望发生的可观察变化；
- 标出最可能被意外破坏的行为；
- 找出当前最大的未知，并选择能最快减少它的动作。

好的起手结果通常只是几句清楚的理解和下一步，不需要任务登记表。

只有当工作会跨会话、跨人或跨多个独立切片时，才需要维护计划与进度。计划的作用是让工作可以可靠续接，而不是证明任务“已进入流程”。

### 5.2 产品意义还不清楚：用例子把它说清

AI 应先从仓库、issue、现有界面和用户描述中解决事实问题，只把真正属于用户的产品选择留给用户。

实用做法：

- 从典型用户动作开始，描述触发、结果和失败时的体验；
- 用两三个具体例子和反例检查同一句需求是否存在不同解释；
- 对多状态或多规则问题画一个小状态图、决策表或事件时间线；
- 明确哪些现有行为必须保留，哪些想法本次不做；
- 只在不同解释会导致明显不同产品时提问。

产出的重点是共享理解。简单且没有新产品语义的变化可以由代码、测试、现有注释或 changelog 表达；新增、明显行为变化以及会被多个消费者或未来版本使用的语义，必须更新现有产品/合同或其他当前真相 owner；没有合适 owner 时才建立最小可发现的承载位置。只有任务需要跨会话、跨 owner 或多个独立切片可靠续接，且既有长期 owner 无法同时承担进度导航时，才增加 change record。任何材料产品语义都不能只留在对话中。

### 5.3 涉及 UI/UX：先走通真实任务，再谈画面

不要从组件列表或漂亮页面开始：

- 选择一个真实用户目标，从入口一路走到完成或恢复；
- 使用接近真实的数据长度、权限和错误，而不是只有理想样例；
- 同时考虑加载、空、部分成功、失败、取消、重试、离线和返回；
- 用低成本原型尽早暴露信息架构和交互问题；
- 在实现后看真实渲染和操作，不用设计稿替代成品证据。

当交互会被反复实现、需要团队协作或包含非显然状态时，维护设计真相；局部、显而易见的调整只需代码、截图或验收说明。

### 5.4 选择技术方向：让方案从仓库里长出来

先理解现有结构、消费者、错误路径、资源生命周期和部署方式，再考虑新模式。

通常比较三种东西就够了：

1. 延续现有约定；
2. 一个更小、更局部的方案；
3. 在当前驱动下确实有优势的另一方案。

对真正影响选择的地方做 spike、测量、合同测试或设计消融。不要为每个选择列形式化矩阵；能解释“为什么这个方案在这里更合适、何时应重看”即可。

只有跨所有权、公共合同、持久数据、长期演进或昂贵回退的决定值得 ADR/RFC。普通局部决定直接体现在清晰代码和测试里。

### 5.5 开始实施：做完整切片，不堆半成品

从最小的端到端结果开始，而不是先铺满所有层：

- 一个切片应包含它需要的代码、错误处理、测试和知识更新；
- 尽早运行最窄的有效检查；
- 新事实与原设计冲突时，停下来修正理解，不机械完成旧计划；
- 行为变化与大规模重构尽量分开；
- 新抽象必须对应已经出现的稳定概念、变化轴或所有权边界；
- 两次类似修补没有进展时，重新检查假设或简化设计。

提交边界可以跟随这种切片，但本地实现完成不自动授权提交。

### 5.6 测试：从可能犯的错出发

测试不是一个后置阶段。理解需求时已经在形成黑盒场景；观察实现时才知道白盒风险。

先问：

- 如果实现错误，用户会看到什么？
- 哪个边界、状态、组合、并发或恢复最容易出错？
- 现有测试为什么会失败，而不是为什么会通过？
- 哪些环境是本次真实观察过的？

然后选择最有辨别力的组合：单元、属性、模型、合同、集成、UI、设备、兼容、性能、探索、mutation 或其他专项测试。不是每个改动都机械拥有所有测试类型；每个重要声明都必须有能推翻错误实现的证据。

对新增或明显行为变化，默认同时做两次覆盖推导：

- **黑盒推导**：从用户结果、公开合同、正常/失败/恢复、权限和兼容行为得到测试；
- **白盒推导**：从实际分支、状态、错误路径、边界、并发、资源、取消、重试和回滚得到测试。

这两种推导可以落到同一个测试，也可以分别落到单元、组件、集成或端到端层。含有可独立逻辑的代码通常应有单元测试；跨数据库、网络、文件、进程、FFI、平台或 UI 的承诺还需要相应边界证据。对高风险或容易自证的 oracle，使用预修复失败、负向 fixture、changed-code mutation 或独立推导检查灵敏度。

覆盖度不是一个百分比，而是六类缺口是否仍然存在：

1. 需求和用户行为；
2. 风险、失败与恢复；
3. 分支、条件、状态和数据边界；
4. 参数组合、事件顺序和兼容方向；
5. 运行环境、平台和真实集成边界；
6. oracle 是否真的会在目标错误出现时失败。

行、分支和条件覆盖率用于寻找盲区，不能单独证明质量。组合空间大时，优先使用 pairwise/t-wise、property、model、fuzz 或基于历史故障的抽样，而不是做盲目的笛卡尔积。mutation 优先作用于本次变化和高风险逻辑，并过滤无行动价值的 mutant。

测试预算分三层：

- **核心覆盖**：主要成功路径、材料失败/恢复、关键边界、已改分支、公开合同、回归和高后果风险，默认完成；
- **扩展覆盖**：常见组合、受影响平台、历史缺陷和有可信发生机制的异常，根据风险继续；
- **极边缘探索**：低概率且低后果、需要巨大组合或环境成本的场景，默认记录为非目标；只有用户明确要求广泛探索，或它虽低概率却可能造成安全、隐私、资金、数据损坏或不可恢复后果时才提升。

停止标准不是“想不到更多测试”，而是材料需求、风险、变化结构和目标环境都已有敏感 oracle，剩余缺口只属于低概率低后果空间，新增测试不再覆盖新的义务或杀死有价值 mutant。

项目级测试策略要回答长期问题：哪些层保护什么、测试在什么环境运行、fixture 怎样隔离、哪些通道快速反馈、哪些通道验证真实平台，以及覆盖缺口怎样升级或接受。它不是每个任务重复填写的测试计划。

#### 怎样实际扩大有价值的测试覆盖

新增或明显变化先从两边找测试，不先填检查表：从用户行为向内找黑盒场景，从最终实现向外找白盒风险。黑盒侧重点是主要结果、材料失败与恢复、权限、兼容和公开合同；白盒侧重点是本次真正改过的分支、状态、边界、错误路径、并发、资源、重试、取消和回滚。两边交叉后再决定测试落在哪一层。

- 独立、确定的业务规则优先用快速单元测试、table-driven tests 或 property tests，便于覆盖大量输入和分支；
- 模块协作、数据库、网络、文件、进程和消息流使用组件/集成或合同测试，避免 mock 把真实边界绕掉；
- 用户流程、公开 API、CLI、UI、设备和平台承诺使用黑盒、端到端或真实平台测试，只对本次声明所需的边界付出成本；
- 性能、安全、隐私、迁移、兼容、并发和恢复按真实风险增加专项测试，不因为“测试类型齐全”机械全选。

覆盖不足时，根据盲区选能扩大测试空间的方法：

| 发现的盲区 | 优先使用的方法 |
|---|---|
| 输入范围和边界不清 | 等价类、边界值、table-driven、property-based testing |
| 规则组合和状态转换容易漏 | 决策表、状态模型、model-based testing、受约束 pairwise/t-wise |
| 输入空间巨大或解析器健壮性不足 | fuzzing、grammar/model-based generation、历史故障种子 |
| 很难直接知道正确答案 | differential、metamorphic relation、reference model、invariant |
| 失败、重试、恢复和资源生命周期不足 | fault injection、negative fixture、time/control substitution、replay/rollback |
| 旧代码缺少保护 | characterization/golden-master 加少量关键语义断言，再逐步替换脆弱快照 |
| 测试可能执行了代码却抓不住错误 | 预修复失败、changed-code mutation、semantic mutation 或小型 seeded fault |
| API、协议或多版本消费者容易分叉 | contract/consumer tests、compatibility matrix、双向/混合版本测试 |
| 并发和顺序问题 | controlled scheduler、linearizability/invariant checks、重复与随机化调度 |

line、branch、condition 和 coverage diff 用来找到没有走到的代码，再结合需求与风险判断哪些空白值得补；它们不是目标分数。对新增代码优先检查未覆盖分支和状态，对关键规则再用 changed-code mutation 判断断言是否有力量。组合很多时先用约束 pairwise/t-wise，再把高风险因子的交互强度提高，不展开完整笛卡尔积。

AI 同时写代码和测试时，要主动避免共同犯错：先根据需求/合同独立写出期望，再根据实现结构补白盒风险；必要时引入 property、metamorphic/differential oracle、旧实现对照或 seeded fault。新增测试运行后，还要确认项目原生 runner 确实发现了它们，跳过、重试、缓存、fixture 污染和环境替代没有制造假绿。

新项目从一个会失败的快速逻辑测试、一个穿过真实关键边界的黑盒切片、项目原生运行入口和最小 CI 反馈开始，再随真实功能扩充。旧项目优先补当前变化暴露的覆盖盲区、修复不可信测试并接入已有 runner/CI；除非已有体系确实承载不了需要的证据，不另建平行万能测试框架。

停止仍由价值决定：核心行为、材料失败/恢复、已改结构和可信高后果风险已经有敏感测试后，剩余只是低概率低后果且成本很高的组合，就记录缺口并停止。用户明确要求广泛探索，或罕见场景涉及安全、隐私、资金、数据损坏和不可恢复后果时，再继续深入。

### 5.7 接近完成：重新看最终结果

在最终 diff 上重新对齐：

- 用户要求的行为真的出现了吗？
- 受影响的消费者、状态和错误路径是否一起处理？
- 是否引入了没有当前价值的复杂度？
- 测试是否会抓住目标缺陷？
- 文档、注释、配置和运行方式是否仍然说真话？
- 本地、CI、模拟器、设备、安装、部署和生产证据是否被正确区分？

审查应该产生具体发现或有依据的无发现结论，不要求额外的“审查产物”。材料变化在宿主具有真实独立上下文且任务可拆分时直接使用干净上下文；否则诚实说明同上下文局限，不把缺少独立能力误写成缺少用户授权。

### 5.8 集成、交付和运行：不要让证据跨界冒充

Git 提交应表达一个容易理解和回滚的变化。是否采用 Conventional Commits、分支策略或 squash 由项目约定决定，不写进全局流程。

发布、部署和迁移是在开发之外增加真实世界约束：精确源码和制品身份、目标环境、凭证、兼容、观察、停止与恢复。它们需要单独授权；构建成功不能推断安装或生产成功。

进入运行后，真实错误、延迟、用户反馈和支持事件重新成为开发输入。反复出现的问题应促使我们改进代码、测试、工具或知识，而不是只增加一句提醒。

## 6. 阶段文档和项目知识怎样贯穿开发

知识沉淀不是开发旁边的一条文档流水线，而是开发主线本身的记忆。RC.7 的默认取向调整为：**材料任务在每个实际发生的环节都留下可被下一环节消费的结果；优先更新已有当前真相，没有合适所有者时再创建文档。**

“每个环节留下文档”不等于每个环节必须新建一个文件。它通常是现有产品/架构/测试文档的修订、一个材料 ADR、测试策略或运行手册；只有需要额外进度导航时才使用 living change record。关键是下一环节能找到、理解并信任，而不是文件数量。

### 6.1 环节之间的文档接力

| 实际发生的工作环节 | 默认读取 | 默认留下或更新 |
|---|---|---|
| 需求理解与澄清 | 用户目标、现有产品/合同、历史行为 | 已确认语义、代表例子/反例、非目标、仍待用户决定的问题 |
| 产品、原型与 UI/UX | 已确认需求、平台约定、现有设计真相 | 用户流程、信息结构、关键状态、错误/恢复、可访问性、原型或设计决定 |
| 技术设计与架构 | 需求/UX 结果、仓库事实、已有架构与 ADR | 约束、备选、选择、边界、数据/状态、失败/恢复、兼容和重看条件 |
| 实施与编码 | 已确认设计、受影响合同、实施计划 | 当前进度、已完成的完整变化、偏离设计的原因、迁移/兼容处理和代码所有者 |
| 测试与验证 | 需求、设计、最终 diff、项目测试策略 | 覆盖义务、用例/fixture、环境、oracle 灵敏度、结果、缺口和未运行项 |
| 验收与交付准备 | 需求到测试的完整链、精确源码/制品身份 | 验收结论、证据边界、已知限制、发布说明、停止/回滚条件 |
| 运行与维护 | 发布身份、runbook、既有 SLO/事故知识 | 真实观察、故障模式、恢复经验，以及应回流需求/设计/测试的学习 |

每个环节开始时先读取前序结果和受影响的长期真相；结束时同时做两件事：更新当前环节的结果，并把已经改变长期事实的内容写回其唯一权威文档。后续环节不得依赖聊天记忆或代理摘要代替这些资料。

新增功能、明显行为变化、跨边界设计和新项目都应更新被实际改变的长期 owner，但不因“材料”这一标签默认新建中心 change record。仅当既有权威文档不能支持可靠续接，而任务又需要跨会话、跨 owner 或多个独立切片继续时，才维护一份最小 change record。它只是导航和当前进度载体，不是 packet、状态机、批准凭证或长期真相的副本。

机械修改、纯只读查询和没有新语义/设计/运行知识的局部修复不创建独立 change record；它们只更新被实际改变的现有文档、注释、测试或 changelog。

### 6.2 知识放在哪里

- `AGENTS.md`：只放进入仓库前必须知道的边界、入口和黄金命令。
- README/索引：帮助找到组件和更深真相。
- 产品/合同文档：保存当前用户可观察行为。
- 架构文档：保存当前系统边界、数据和运行模型。
- ADR/RFC：保存长期选择的原因、备选和重看条件。
- 测试策略：保存项目怎样建立可信反馈。
- runbook：保存需要人工判断的操作、观察和恢复。
- 工作计划：只服务当前长任务，完成后有价值的内容回到上述长期所有者。
- 源码、schema、manifest、测试和 CI：拥有可以执行或自动验证的事实。

同一事实只有一个主要所有者，其他地方链接过去。生成的地图和报告只是可替换证据，不晋升为项目政策。

### 6.3 新项目和旧项目

新项目在第一次产生需要持续维护的非代码知识时，必须把它放入可发现的项目原生入口，但不预建空壳。小型库可由 README 承担入口；当出现多个长期知识域或需要独立导航时，建立 `docs/`/`docs/index.md` 或项目等价结构。非平凡项目最终至少应能发现：产品/合同真相、架构与材料决定、测试策略、进行中的变化和需要人工判断的运行知识。入口负责导航，不复制全部内容。

旧项目优先尊重已有知识位置和命名。若现有体系能完成上述接力，就沿用并补链接；若没有可发现、可维护的工程文档入口，则在当前变化范围内建立 `docs/` 或项目原生等价入口。RC.7 不为了统一外观整体搬迁稳定文档，但也不以“旧项目”为理由继续依赖聊天和口头知识。

### 6.4 文档质量和停止条件

每次环节交接检查：

1. 下一环节需要的语义、决定、限制和未决问题是否可找到；
2. 长期事实是否回到唯一 owner，而不是只留在 change record；
3. 文档是否链接到真实源码、合同、测试或命令，而非宣称自己就是执行证据；
4. 旧结论是否被修订、标记 superseded 或写明重看触发；
5. 是否出现重复事实、空模板或只为证明流程存在的段落。

文档完成的判断是它能让下一环节和未来维护者做出正确行动。达到这个目的后停止扩写；行数、文件数和评审轮次都不是质量指标。

## 7. 方法论怎样进入这条主线

方法不是必须报到的步骤，而是遇到困难时可以拿起的思考工具。

常见信号包括：

- 一句话有多种产品解释；
- 状态或规则相互作用太复杂；
- 两个技术方向各有可信优势；
- 某个抽象或组件的必要性说不清；
- 测试没有可靠 oracle；
- 修复反复失败；
- 变化涉及安全、隐私、并发、迁移、FFI 或不可逆后果。

一次只使用能改变当前决定的少量方法。方法可以只存在于思考和代码变化中，不要求写“方法执行记录”。如果方法没有带来新信息、淘汰方案、简化设计或增强证据，就停止使用。

消融实验的正确位置正是在这里：当某个设计成分的价值不清楚时，用移除或替换来观察能力和复杂度变化；没有这样的结构时不需要消融。

## 8. 模型和子代理也服从同一原则

- 没有独立工作面时由当前代理直接完成；一旦独立子任务能带来净进度、专业性或干净上下文价值，就主动委派。
- 更强模型或更深思考用于语义模糊、架构、跨边界和高后果判断，而不是因为文件多。
- 子代理只用于真正可独立推进的研究、实现或干净上下文审查。
- 计划、调试、测试和最终判断高度相互依赖时留在同一主线。
- 根代理查看实际源码、diff 和测试，不以子代理摘要替代证据。

**启动子代理以及子代理继续启动子代理，不需要额外向用户申请授权。** 它们是模型内部的工作分配手段；模型发现独立研究、并行实施、测试执行或干净上下文审查具有净收益时，可以直接派发。独立审查也不再因为“没有单独授权”而降级；只有宿主未提供真实独立上下文、并发/资源不足或任务不可安全拆分时才降级。

不需要授权不等于可以扩大工作边界。每个后代继承当前任务已经拥有的目标、仓库/路径、修改、工具、数据、外部动作和破坏性操作边界；spawn 本身可以直接发生，但 commit、push、发布、部署、安装、外部通信、敏感数据访问、破坏性清理或新增语义/仓库/依赖仍按它们各自的授权规则处理。子代理提出扩展建议也不能自行实施。

派发前要能说清子代理的独立工作产品、oracle 和主线怎样消费结果。父代理可以在同一边界内直接进行嵌套委派，并发量由真正独立的工作面、宿主容量、共享文件/设备资源和协调成本决定；审查已经没有未解决的后果性问题时，不为清除命名、措辞或个人偏好继续增加 reviewer。长任务的每个完整切片都要以一个已证明结果、明确阻塞或材料新风险结束，不能仅以“还有计划项”无限延长。

现有 P0-P6/`route-agent` 体系继续负责自动选择模型、reasoning effort 和 context fork：封闭机械任务偏向快速模型，普通探索/因果工作使用均衡模型，开放跨边界和高后果判断使用更强模型。P0-P6 普通派发不触发用户确认；PX、另行计费的批量模型试验和 Bench campaign 仍是例外预算事项。路由结果只指导派发，不证明质量，也不需要保存 receipt。

模型路由和代理分工是提高质量/速度的工具，不是开发阶段。

## 9. 只有少数事情是真正的硬边界

RC.7 应谨慎使用“必须”。以下边界值得保持强约束：

- 不扩大用户授权，不把实现等同于 commit、push、发布或部署；
- 不覆盖、重置或归因用户拥有的修改；
- 不用猜测替代可以从仓库或运行获得的事实；
- 不在没有新鲜证据时声称完成或通过；
- 不把一个环境的证据冒充另一个环境；
- 不隐藏材料歧义、失败、未运行项或不可恢复风险。

材料任务的文档接力和证据诚实属于默认约束，但不固定文件数量、模板或每阶段独立文件。ADR、测试种类、提交方式、审查轮次和方法数量仍由当前任务的未知、后果、波及和可逆性决定。

这里的“授权”不包含普通子代理派发；子代理和嵌套子代理可以在已授权任务边界内直接使用。硬边界约束的是它们可能执行的实际动作和范围扩张，而不是代理数量。

## 10. RC.7 应怎样实现成 Skill

### 核心 Skill 保持薄

核心只需要：工程取向、自然开发循环、何时加载专题 Skill、少数授权/证据底线，以及“材料环节留下可供下一环节消费的文档并回写长期 owner”这一条知识原则。不要把本文件的文档拓扑、文件选择和交接细节塞进主入口。

### 专题 Skill 负责可操作指导

需求、UX、架构、依赖、调试、测试系统、验证、审查、知识和交付各自描述：何时有帮助、怎样下手、常见失败、什么时候停。现有 `repository-knowledge` 负责当前真相、ADR、测试策略、runbook、索引和新旧项目适配，并仅在既有 owner 无法支撑可靠续接时建立最小 change record；主 Skill 不再复制一套文档 Skill。它们可以组合，但不互相制造固定阶段。

### 方法库作为按需参考

入口 Skill 不列出 100 多个方法。专题 Skill 在遇到具体机制时读取相关方法卡；方法卡提供简洁做法、适用/不适用信号和例子。

### 自动化只固定确定性的东西

CLI 和脚本适合检查 schema、链接、测试发现、工作树、制品身份和其他确定性事实。产品理解、设计质量和文档价值不应通过字段齐全来伪装成可机器判定。

### 用真实任务而不是流程覆盖率评价 RC.7

建立一组代表性任务：机械小改、明确缺陷、模糊新增、旧项目重构、UI、跨语言、迁移、新项目和发布准备。比较有无 RC.7 时：

- 最终行为是否更正确；
- 是否更早发现关键未知；
- 是否减少过度设计和范围漂移；
- 测试是否更有缺陷敏感度；
- 知识是否帮助了后续任务；
- 普通任务是否仍然快速安静；
- 总交互、上下文、时间和模型成本是否值得。

如果一条指导没有解决真实失败，或持续增加成本而不提高结果，就删除、缩短或降为按需参考。

本地 dogfood 还要求加入三类停止行为：同一语义目标内不重复路由；方法已经改变当前决定后立即返回开发；审查只剩非后果性偏好时结束。它们与最终行为正确性一起评价，不能被“Skill 已激活”或“finding 已清零”替代。

## 11. 对上一版草案的明确处置

以下设计不再进入 RC.7 主线：

- T0–T6 任务编号；
- 所有阶段共享的入口/输出/退出/重开合同；
- 新增变化固定三轮打磨；
- 每阶段固定创建独立文件和填写相同模板的文档矩阵；
- 为普通工作记录方法、状态、WAIVED 或完整证据账本；
- 以流程覆盖率或文档存在判断质量。

保留但改为指导的内容：

- 从需求到运行的完整关注范围；
- 新功能通常应先澄清产品意义；
- 完整用户状态、最小充分设计、端到端切片；
- 黑盒和白盒互补、项目级测试策略；
- 功能点式 Git 集成；
- 知识、代码和测试随变化保持一致；
- 材料任务从需求到验收持续留下可由下一环节消费的文档链；
- 高后果工作增加专业方法和更强证据。
