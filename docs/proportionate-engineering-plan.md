## 目标与成功标准

保持完整授权目标及必要质量，减少不能带来相称收益的设计和验证。小批实施不缩小用户的整体要求；不以代码行数、测试数量、提问次数或流程完整度代替结果。

| 目标 | 希望改变的行为 | 必须保住的边界 |
|---|---|---|
| 需求与架构不过度设计 | 先判断某项保证是否值得承诺，再设计机制；主动提出足够简单的方案，允许省略没有依据的额外能力 | 不能擅自弱化已接受的产品语义、真实消费者契约或必要的数据与安全责任 |
| 代码防御与实际边界相称 | 把验证、错误处理和恢复放在有实际责任的边界，减少重复检查、静默兜底、无消费者恢复状态和通用包装 | 外部输入、持久数据、权限、资源生命周期、可达的并发/数据损失风险仍需正确处理；无历史事故不等于无需保护 |
| 验证与维护成本相称 | 复用仍有效证据，围绕本次变化和未解决结论选测；辅助设施修好观察能力后停止 | 保留首次失败、必要回归、原生环境边界和正式交付检查；少跑测试本身不算收益 |

跨越三个目标的成功条件：AI 能说明保留/省略了什么、用户得到什么、接受什么限制、哪些责任由现有机制承担。理由按需要放进现有答复/设计，不要求逐项表格或固定格式。

## 一、先决定保证，再决定机制

检查遗漏场景时，区分当前目标/明确承诺、真实消费者、重大后果，以及仅能想象的额外能力。可达风险可由接口、调用链、平台约束或具体反例支持，不要求先发生事故或有精确概率。

1. **AI 可以直接不采用**：未被要求、未形成契约、无真实消费者或重大后果支撑的额外设计。例如单执行方任务不引入可插拔编排层；一次手动导入不自动扩展到跨端续接。重要范围限制在正常方案说明中交代，无须逐项提问。
2. **AI 可以在已授权改动中直接精简**：保留既定行为与责任的重复实现、没有消费者的内部机制。必须核对调用者和生命周期；“没有找到”尚不足以证明消费者不存在时，继续有界调查或保留，不能静默删除。
3. **需要用户决定**：简化会改变已接受的一致性、离线/重启恢复、兼容、撤销或可见结果。先调查技术事实，再说明足够简单方案满足什么、接受什么限制，以及更强方案增加的用户收益和长期成本；给出推荐。放进现有业务讨论或整体方案确认，不增加固定审批轮次。
4. **必要边界继续保护**：安全、权限、数据完整性及不可逆后果不能仅凭低频或未主动提出而省略；保护方式仍应选最小有效机制。既有可协商保证不是永久不可改变，但改变它需要相应的用户决定。

示例：路由切换可比较“远端权威、查询与已有同步收敛”和“更强即时一致保证加专门协调”。只有在前者满足确认后的业务规则时才能采用；不能从用户说“简单一点”推定所有强保证已被放弃。

已有重要新功能首次实施前的整体理解确认、接受子集、纠正传播、撤销与交付授权边界保持不变。用户要求完整理解，应覆盖完整目标与关键关系；不自动承诺每个可以想到的流程。

## 二、把防御放在真正拥有责任的位置

架构与代码审查沿现有调用/数据路径判断：防什么输入或失效、哪一层拥有责任、现有机制是否已保证、去掉后会损害哪个结果。只对有争议或高成本的机制展开，普通检查不需要写论证单。

- 外部输入、落盘数据重读、跨进程/协议边界仍不可信；内部类型已经保证的条件，可优先依赖类型与集中验证，避免各层重建同一检查。
- 错误传播、资源释放、取消/关闭、幂等、必要的持久恢复按实际职责保留。静态可达失败和平台失效模型足以支持保护，不以“尚未复现”作为删除理由。
- 不为每条简单调用默认增加持久状态机、重试/补偿、备用存储、通用结果包装或多层兜底。新机制须有当前责任；现有机制则先核实是否可删或合并。
- 不把捕获后返回空值、默认成功、无条件重试包装成健壮性。不能把契约内应处理的输入、可恢复失败或资源责任转成无说明的崩溃；内部不变量破坏按语言与仓库约定处理，不为程序缺陷自动增加恢复承诺。
- 正常成功与超时/取消/恢复分支分别验证。故障分支的处置凭证只在该分支被触发时要求；正常完成仍须满足本身的结果、资源与安全条件。

这轮改的是 Dev Flow 的指导，不借机审计或修改 PushGo/Aegir 产品代码；不放宽 DLP、Hook、秘密或权限检查。若以后确实发现相关误报，作为独立、有正反例的因果修复处理。

## 三、按变化失效证据，按决策价值追加验证

重跑之前，在已有上下文中判断：旧证据覆盖的结论、本次变化能否影响该结论，以及新结果会改变什么决定。普通任务无需新清单或记录文件。

- 证据输入包括相关源码及传递消费者、测试断言、fixture、runner/选择器、配置、生成物、工具链、目标环境与拟交付制品。仅产品源码未变不等于证据有效。
- 中间修补以最后有效证据以来的相关变化和未解决结论为基准；不能把每次修补都自动升级为累计 PR 全部验收。跨模块影响可能使累计范围中的部分证据失效，需明确纳入。
- 无可靠依赖图或身份不明时，说明未知并做最小保守的受影响检查；不能凭“看起来无关”缓存成功，也不自动建设选测平台。
- 首次失败保留。后续成功只说明该次观察，不能抹掉原失败或把未解释的 flaky 改写成稳定通过。观测修好先验证发现/判定有效，再跑受影响产品检查。
- 负对照用于不可信或后果严重的 oracle，复用已经有效的敏感性证据；不要求每次运行都新做故障注入。辅助设施两次未推进主要结果后，沿现有规则简化、替换、延期或标阻塞。
- 冻结交付候选仍按仓库交付规则核查证据完整性；需要的原生/平台/集成检查不得以“此前跑过类似命令”为由跳过。未覆盖范围明确 NOT RUN / BLOCKED / WAIVED，禁止补成 PASS。

用户明确要求完整重跑、重复运行观察不稳定性或更广探索时，执行该授权目标；复用规则不能覆盖明确请求。已有约束仍适用，遇到真实资源或权限限制时如实报告。

## 判别场景与验收

以下是设计审查/后续实现的有限场景，不是新增的自动模型评测，也不强制每项写测试文件。每项同时有防止过度工程和防止保护不足的边界。

| 场景 | 应有结果 | 必须拒绝的退化 |
|---|---|---|
| 手动导入，单设备，未承诺跨重启续接 | 直接设计主流程，合理失败可重试，不自动加持久编排/跨端协议 | 已接受“重启后继续且不重复入账”时仍省掉必要状态 |
| 路由切换的强一致与最终一致选择 | 先比较用户结果/限制/协调成本，主动推荐足够方案，等待真正的语义决定 | 把“精简”当成已批准丢弃旧承诺，或要求用户自己设计协议 |
| 入口验证后的内部值 | 可合并相同责任的重复判断，保留清晰的失败表达；内部不变量可按仓库惯例断言，不增加默认恢复承诺 | 误把不可信落盘/跨进程数据当作已验证内部类型，删除必要保护；或把契约内应处理的失败改成断言崩溃 |
| 正常任务已完成，未触发超时终止 | 按正常成功与资源条件判断，不索取超时分支凭证 | 真实超时终止时跳过进程归属或资源安全检查 |
| 既有局部修补加无关说明文档变化 | 复用不受影响的有效结果，只补修补影响与未解决结论 | fixture/runner/工具链变化仍复用旧 PASS，或跳过冻结交付要求 |
| 首次失败、观测修复后成功 | 分开原失败、harness 修复与新观察；受影响范围重验 | 将重试成功覆盖首次失败，或为追绿扩大超时/重复全套 |
| 精简中发现无阻断关系的旁支缺陷 | 保持精简排序，单独说明风险；严重且阻断主目标的缺陷可成为前置 | 以 bug 数量替代机制收益，或为追求精简隐瞒严重风险 |

### 验证层级与停止

1. **方案阶段**：已完成三轮独立上下文审计；每轮稳定目标，收到后根代理核实并修订，下一轮审查修订版。该阶段只检查新增文档的链接与 diff，不跑产品测试。
2. **规则实现**：只修改有实际契约变化的现有断言；可加少量静态边界检查，但不得把关键词存在当作模型理解证明。每批跑受影响断言；最终一次 suite/context/knowledge/plugin/contract validators 与 `git diff --check`。发布资格另按 AGENTS 执行，不能提前声称；本次实际结果见末节。
3. **真实行为收益**：现有 3 案例/8 次启动观察先于本计划，只能当历史基线。新的场景审查和静态绿色均不证明成本降低；本轮不运行模型 A/B、裁判或批量任务。未来如要求实证，另定最小可区分输入、预算及停止条件。

本方案不设“测试减少 X%”“代码减少 Y 行”等虚假指标。静态完成标准是 owner/消费者无冲突、正反例决策一致、现有上下文预算未提高、授权与必要质量没有削弱。真实使用中若出现擅自降保证、漏必要防护、错误复用证据或反复多问，应保留首个反例，只修所属边界，必要时退回该条指导；不自动开全项目审计。
